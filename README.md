# commitlint-rust and commitguard

Two independent Rust crates separate message linting from Git identity enforcement:

| Package / command | Responsibility | Runtime dependencies |
| --- | --- | --- |
| `commitlint-rust` / `commitlint` | All 38 Commitlint 21.2.3 message rules | None for stdin/explicit files; Git for history/edit lookup and enabled trailer-exists |
| `commitguard` / `commitguard` | gh identity, attribution, hooks, outgoing history and setup | Git and authenticated gh; OS shell for hooks |

`commitguard` embeds the lint library at build time, so it does not require an installed `commitlint` command. `gh-commit-guard` remains a compatible executable entry point. Cargo/Rust, Bun, Python and JavaScript dependencies are development tools only.

The no-config command and commitguard policy are fixed: conventional type/scope/breaking-marker grammar, conventional type enum/case, subject empty/case/full-stop, trimmed header; printable ASCII with LF; at most 128 characters in the entire message including internal newlines, body and trailers, excluding terminal LF. Blank-line warnings do not become blockers. English is a writing requirement, not a grammar classifier. The selected lint rules are compared with 221 golden cases generated by Commitlint 21.2.3 with config-conventional and ignores disabled. The source build also provides a separate opt-in JSON configuration mode covering all 38 upstream rules. JavaScript configuration, plugins and custom parser regular expressions are unsupported and rejected explicitly.

The independent guard checks both raw main identities against the authenticated human github.com account, permits recognized AI attribution, and checks every outgoing commit against the actual live push destination. It rejects signed/nonstandard commit objects. Hook chaining, message editor cleanup and linked worktrees are preserved. Installation activates strict mode explicitly; public devflow's default remains legacy.

```sh
cargo test --workspace --locked
cargo build --workspace --locked --release
./target/release/commitguard account
./target/release/commitguard message /path/to/message.txt
./target/release/commitguard install --home /tmp/isolated-home
```

Use an isolated HOME/GIT_CONFIG_GLOBAL/CODEX_HOME/CLAUDE_CONFIG_DIR for installation tests. Production setup changes user-level Git configuration and agent instructions; reopen shells afterward. `install --skills-only` installs native portable skills without global Git/shell activation. Containers use `install --container --repo <workspace>` and refuse host-mounted agent realpaths.

The PATH entry point guards ordinary no-verify and hooksPath overrides. Absolute/unwrapped Git, API writes, direct modification of the guard/configuration, and internal plumbing are beyond this local boundary. Native hooks block violations; automatic correction remains an agent workflow constrained to proven task-owned unpublished clean linear history, with backup refs and identical trees. No automatic force push. The pre-rebase gate checks source authors and credits, permitting malformed input wording to be reworded. Sequencer picks can retain invalid local messages; the agent must validate every resulting object, and pre-push remains the full outgoing-history backstop.

In the current source build, normal identity checks use a private cache bound to
local gh credentials, selected account, configuration directory and gh executable.
They make no API request. Initialize or refresh it with `commitguard --strict account`;
a missing, changed or invalid cache refuses the check. `--strict` always verifies
online and never falls back to cache. Push/pre-push and `fix --apply` always verify
online, including checks before and after a rewrite. Normal cached checks cannot
detect server-side revocation until the next strict check. No tokens are stored.

Do not replace an installed binary or policy while an active history-repair task binds its hash. Building and copying source bundles does not activate them on the host.

## Batch correction (source build)

`commitguard fix` exports the original messages and findings for an exact
unpublished linear suffix. Edit only candidate messages with an external editor
or LLM; commitguard does not upload data, call an LLM, guess wording or truncate
messages. The message-only `commitlint` command remains a validator.

```sh
commitguard fix --range origin/main..HEAD --plan ../fixes.json
# Edit ../fixes.json, preserving the plan_id and ordered source_oid values.
commitguard fix --preview ../fixes.json
commitguard fix --apply ../fixes.json
```

The editable JSON contains `plan_id` and `candidates`, with each candidate holding
`source_oid` and `message`. Original source/identity/ownership data is stored in
a private SHA256-bound receipt under the common Git directory. Proposal and
ownership files must be outside worktrees or under that Git directory; do not
make the source checkout dirty with root-level JSON files.

Apply requires an existing guard installation, online gh authentication, Git
2.38 or newer, a clean named-branch worktree, an excluded existing base and
complete linear history. It checks all configured fetch/push destinations;
missing remote objects, unavailable destinations and zero remotes refuse repair.
Fetch the relevant advertised refs and objects before planning; the checker never
ignores unknown remote ancestry. HTTP remote URLs containing credentials are
refused: use gh authentication instead. Proposal parents must be private to the
current user. Install or upgrade first, then export a new plan; setup changes
invalidate existing receipts.
The publication check covers advertised history, not hidden refs or unknown
forks. Windows, root/merge/published history and unsupported repository features
are refused. Git and gh remain the only runtime executables besides the OS shell
used for hooks; Python, Bun and git-filter-repo are not required.

Ordinary repair preserves canonical source Authors and fixes wording/Committer.
For an explicitly identified mistake in the operator's own Author metadata:

```sh
commitguard fix --range origin/main..HEAD --author gh --ownership ../owned.json --plan ../migration.json
commitguard fix --preview ../migration.json
commitguard fix --apply ../migration.json --confirm-author-migration <apply-digest-from-preview>
```

Ownership JSON has `sources` entries containing `source_oid`, the exact raw
`old_author` header value (including timestamp/timezone), and `owned: true`.
Every noncanonical source Author in the suffix must be declared. The declarations
are frozen at planning: editing the ownership file later does not grant more
authority. They document an explicit ownership assertion, not cryptographic
proof of authorship. Agents must have the owner's explicit instruction covering
the exact OIDs/old Authors; an LLM must never invent ownership. Destination
Author and Committer are always the authenticated gh account. Preview binds the
normalized complete messages to the apply digest; edit then preview again.

Replacement commits are constructed through ordinary guarded Git in a detached
worktree, with existing hooks active. Every actual message, identity, tree,
parent, count and Author date is checked before expected-old-tip promotion.
Recognized attribution must be retained and counts toward 128 characters. The
operation records backup refs and a durable original/new OID mapping; it never
pushes. A failed or interrupted operation retains its journal, backup and staging
evidence and reports actual state. Do not automatically reset refs, break locks,
force-remove dirty worktrees or delete backups. Backups retain old violating
commits and must not be included in broad mirror publication. V1 supports
idempotent retries of completed operations; interrupted or failed operations
require manual recovery after inspecting the journal, actual refs and staging
state. It does not automatically resume, abandon or break their retained locks.

Published v0.2.0 archives and an existing host installation are unchanged by
building this source feature. A release/installation upgrade is a separate step.

## Development oracle

`crates/commitlint-rust/tests/fixtures/commitlint-golden.json` records upstream-derived inputs/results. Upstream Commitlint is never called by the shipped binary. Integration tests use isolated temporary repositories, real Git and fixture gh, with no Bun or Python on runtime PATH. Platform binaries are built from Cargo.lock; only actually built targets are distributed.

The source also includes 86 assertions from nine pinned upstream rule test files,
with original test titles, line references, source hashes and license notices.
Individual rule expectations live in `upstream-rules.json`; the same inputs are
evaluated separately against the complete fixed policy in `upstream-input-policy.json`.
Those 86 policy records cover 32 distinct messages and retain one record per
original assertion so their provenance remains traceable.
An individual rule passing does not imply that the complete policy accepts the message.
The oracle preserves upstream lint results independently of parser failures and
records intentional policy differences, including rejection of empty messages.

`lint_detailed()` exposes parsed header/type/scope/subject/body/footer fields and
fixed-policy error and warning diagnostics. `lint_message()` retains its existing
acceptance and errors. The source CLI's leading `--verbose` option prints these
diagnostics; warnings do not reject a message.

### All-rule JSON configuration (source build)

The native rule API implements all 38 exported rules from Commitlint 21.2.3,
including Unicode case rules, scope delimiters, references, sign-offs and trailers.
`lint_configured()` and explicit `--config FILE.json` use an independent ordered
configuration. Disabled rules never execute; warning-only failures return success.
The config is validated before empty-message or default-ignore shortcuts.

```json
{
  "extends": ["@commitlint/config-conventional"],
  "defaultIgnores": false,
  "rules": {
    "header-max-length": [2, "always", 128],
    "scope-enum": [2, "always", {"scopes": ["api", "cli"], "delimiters": ["."]}],
    "trailer-exists": [2, "always", "Signed-off-by:"]
  }
}
```

```sh
printf 'fix(api): correct parsing\n\nSigned-off-by: Example User <user@example.com>\n' | commitlint --config ./commitlint.json
```

`extends` supports the built-in conventional preset (upstream's 100-character
header/line limits), and a rule override replaces its entire tuple. Severity is
0 (disabled), 1 (warning), or 2 (error). Default ignores are enabled in this mode,
and can be disabled as above. This mode accepts Unicode and does not enforce
commitguard's ASCII, whole-message 128-character or gh identity policy.

Parser options support the `conventional-changelog-angular` and
`conventional-changelog-conventionalcommits` string presets,
`commentChar`, `issuePrefixes`, `issuePrefixesCaseSensitive` and `referenceActions`.
References affect footer recognition and include issue/owner/repository metadata.
An object-form `parserPreset` with explicit `parserOpts` replaces inherited
options and uses the default Angular grammar plus those options. A metadata-only
object retains inherited options; its optional `name` does not load a module.
These follow the upstream loader. Only the canonical preset names above and
`@commitlint/config-conventional` for `extends` are supported.
Custom parser expressions, arbitrary `extends`, executable ignores, plugins and
JavaScript configuration are rejected rather than silently approximated.
Enabled rule values require the supported number/string/list/case/scope schema;
unsupported fields and explicit null values are rejected.
Only an enabled `trailer-exists` invokes `git interpret-trailers --parse` on the
original message. A missing/failed Git process, deadline or output-limit failure
is a fatal operational error even for a warning or `never` rule. Other rules
need no runtime executable; the linter never accesses gh or the network.

The full upstream corpus records 532 functional tests, 3 registry/documentation
tests, 632 original assertions and 532 rule calls across all 38 rules. Rust checks
every rule's Boolean and exact optional diagnostic against these frozen outcomes.
It independently compares all six parsed fields and references for 525 calls;
the other 7 type-case calls use upstream's custom header expression and supply
its frozen parsed record directly to the rule API. Custom expression parsing
remains outside the native configuration profile. Separate case fixtures cover
2,844 transformations/decisions and 13 subject gates, frozen to Node 26.8.2,
Unicode 17 and es-toolkit 1.52.0. Original assertions and observed results are
stored separately, with source hashes and locations; mismatches fail generation.
Native input handling is preserved: edit files retain their original raw text,
while configured `--edit` defaults to `#` comment/scissor filtering. An explicit
JSON `commentChar` overrides that default; an empty string disables filtering.
`core.commentChar` is not implicitly loaded, explicit files need no Git,
history requires UTF-8, and the
configured API retains upstream lint's valid empty-input and empty-rule outcomes.
These differ from the upstream CLI's input filtering and loader safeguards.
Trailer deadlines apply per evaluated message, not to an entire history range.
A separate 111-case JSON-file oracle runs the actual upstream loader, lint and
parser, covering tuple overrides, ordering, severity spellings, ignores and
parser-option inheritance. Strict native-profile refusals are labelled separately
from the observed upstream outcomes.
This is full rule coverage, not full compatibility with every upstream CLI,
JavaScript loader, plugin or custom parser feature.

After installing the pinned development dependencies in `tests/oracle`, regenerate
and check the fixtures with:

```sh
node tests/oracle/generate.mjs
node tests/oracle/generate-upstream.mjs
node --experimental-vm-modules tests/oracle/generate-full-upstream.mjs
node tests/oracle/generate-unicode-properties.mjs
node tests/oracle/generate-configured.mjs
node --experimental-vm-modules --test tests/oracle/*.test.mjs
cargo test --workspace --locked
```

The vendored upstream test files are validated before regeneration. These
development commands add no Node or Bun dependency to the installed binaries.

The workspace lives under `crates/commitlint-rust` and `crates/commitguard`, with dependency direction guard → lint. The lint package contains no identity, account, hook, installer or guard-configuration code. Frozen oracle tooling remains at `tests/oracle/`.

## Clone-free installation

Install the published commitlint-rust and commitguard package with one command:

```sh
curl -fsSL https://github.com/tkgstrator/commitlint-rust/releases/latest/download/install.sh | bash
```

Git and an authenticated GitHub CLI (`gh auth login --hostname github.com`) are required. No source checkout, Rust compiler, Bun or Python is needed. The installer verifies the native release archive and installs the global Git guard and Codex/Claude skills. Reopen your terminal after installation.

This downloads the latest published release; unreleased source features are not included. For installation options and independent Homebrew packages, see [INSTALL.md](INSTALL.md).

## Bundled targets and setup

`sh scripts/setup-commit-policy.sh` uses the supplied binary and installs the owner policy once per host. The standalone message command is `scripts/commitlint`; it accepts stdin, `--edit [FILE]` or `--from REF --to REF`. It never requires gh authentication. `scripts/check` provides the identity and push policy commands. `scripts/build.sh [target]` is development-only and requires Cargo/Rust plus an installed target toolchain.

| Target | Validation |
| --- | --- |
| aarch64-apple-darwin | Native Mac unit/integration tests |
| x86_64-apple-darwin | Cross-build only; this Mac has no Rosetta |
| aarch64-unknown-linux-musl | Linux ARM container unit/integration tests |
| x86_64-unknown-linux-musl | Linux x86 container unit/integration tests |

Linux binaries link musl statically. Windows binaries are not distributed; unsupported platforms fail closed. The Rust source separates platform-independent linting from Git hooks/setup so additional platforms can be built and verified separately. Binary manifests record file digests for distribution checks; they are not an immutable trust boundary against direct file modification.

The source skill and references live under `resources/`. The two consumer repositories carry self-contained skill/binary bundles. Templates can be copied independently, without fetching code or compiling at container startup. Changes here must be rebuilt, the resource/binary bundles synchronized, and their manifests rechecked before rollout. `tests/oracle/` is a development-only frozen Commitlint oracle; use the pinned development oracle to regenerate fixtures when changing lint rules. Bun transpiles vendored TypeScript only; Node executes the original callbacks and assertions. No oracle package appears in a runtime bundle.

## Release compatibility

Source v0.2.0 introduces the workspace and canonical guard name. Published v0.1.0 assets remain immutable. The combined archive retains its exact four-member payload for older bootstrap compatibility. Separate `commitlint-only-TARGET.tar.gz` and `commitguard-TARGET.tar.gz` archives serve independent consumers. Native setup installs both guard names and preserves existing hook/config/skill paths. A source build does not upgrade the live host guard.

`scripts/build.sh` records source and payload SHA256 provenance. Packaging refuses stale or modified binaries before writing assets; by default it requires all four supported targets. Explicit target arguments write partial smoke-test archives to a separate `dist/partial/` directory without changing full-release assets or universal Formulae. Build provenance is a development safeguard, not an independent trust boundary against the release publisher.

The tap's new `commitlint` and `commitguard` Formulae provide the independent commands. `commitlint-rust` remains a combined compatibility Formula so existing upgrades retain their old guard and lint commands. It shares the guard commands with `commitguard`, so those two Formulae are alternatives.

### Fast bulk history rewrite (source build)

`commitguard bulk-write --manifest FILE` validates an existing-history batch and
returns its approval digest. `--confirm DIGEST` writes all approved commit objects
in a Git batch and verifies their exact bytes. It runs no per-commit hooks, GitHub
API checks, checkout or index changes. Normal mode uses the verified local cache
once; explicit leading `--strict` authenticates online once. Push still validates
online. This route is explicitly authorized for bulk history rewrites; ordinary
new-commit guards and V1 `fix` keep their existing behavior.

The manifest binds actual source bytes, complete candidate bytes and expected
OIDs. Roots and ordered merges are supported. Both original identity date fields
are retained. Changes affect messages and main identities, with exact ownership,
credit and obsolete-signature declarations. Trees stay identical except separately
approved, independently checked path-specific gitlink substitutions.

This helper creates objects and a durable verified mapping. The coordinating
operator retains backups, exact ref transactions, complete graph verification,
annotated tags and publication. It does not promote original refs or push.
`bulk-write-tags --manifest FILE [--confirm DIGEST]` provides the same object-only
route for annotated tags. It preserves tag names, types, dates and prose; target
changes require a revalidated completed commit receipt or an earlier tag in the
same batch. Obsolete PGP/SSH signatures require explicit removal permission.
Exact approved Claude Code generated footers can become `AI-credit: Claude Code`.
Repeated actor credits can use a factual count such as
`AI-credit: Claude Opus 5.5 x141`, preserving attribution multiplicity within the
128-character limit. Other prose is never inferred as attribution.
Do not replace a live guard while another operation binds its binary/policy hash.
See [the manifest and safety contract](docs/superpowers/specs/2026-10-07-commitguard-bulk-write.md).

### Explicit legacy collision provenance (source build)

For an explicitly approved legacy rewrite, `bulk-write` policy version 2 adds
`"provenance_profile": "source-sha256-v1"` to the manifest and
`"source_provenance": "add"` to each selected entry. An exact positive Author
ownership declaration is required even for a canonical source. The candidate
contains one final `source-sha256 <lowercase SHA256>` header immediately after
Committer, equal to the complete actual original raw commit digest.
This separates otherwise equal normalized commits without changing message words,
dates, trees, ordered parents or attribution counts. The 128-character message
limit stays unchanged; provenance is metadata and supplies no ownership authority.

Later independently approved rewrites use `"source_provenance": "preserve"` and
copy the original header unchanged. Recomputing it from an intermediate commit is
refused. Default policy version 1 still rejects origin-bearing bulk objects;
undeclared v2 entries do too. Ordinary V1 `fix` fails closed on this metadata;
use the explicit bulk preserve route for later authorized history changes.
Tag receipt reuse revalidates the v2 domain and actual source/candidate bytes.
Normal commit/push checks validate known header syntax, current identity and message
policy; historical origin requires the operator's retained approved source evidence
and exact outgoing object mapping. A header alone is not proof of origin.
See [the approved profile](docs/superpowers/specs/2026-10-08-immutable-origin-profile.md).

## Dev Container Feature

Add the `commitguard` Feature to install the native guard, the standalone `commitlint-rust` linter, plus Git and gh on Debian/Ubuntu, amd64/arm64:

```json
{
  "features": {
    "ghcr.io/tkgstrator/commitguard/commitguard:1": {}
  }
}
```

The original URI `ghcr.io/tkgstrator/commitlint-rust/commitguard:1` remains published for compatibility. Installed commands: `commitguard`, `gh-commit-guard`, `commitlint-rust` (no `commitlint` alias, to avoid the npm command). The published v0.2.0 linter supports a limited rule set, narrower than the 38 rules in `master` source.

The guard activates automatically at container start. Authenticate with `gh auth login -h github.com` before committing or pushing; use `commitguard-devcontainer-setup` to retry setup. The Feature pins published native v0.2.0 and verifies both archive digests. See [Feature options and workspace effects](features/commitguard/README.md).
